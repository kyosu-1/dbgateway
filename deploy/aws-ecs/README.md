# AWS test environment (ECS Fargate + RDS for PostgreSQL)

A disposable environment that runs two dbgateway tasks on Amazon ECS (Fargate) to verify end-to-end behavior in the cloud. **It is not a production deployment.** Destroy it as soon as you are done.

Nothing personal is stored in this directory: no account IDs, IP addresses, email addresses or profile names. Pass values with variables and keep the Terraform state locally (`terraform.tfvars`, state files, `tfplan` and `*.pem` are git-ignored).

## What it creates

```
  Test machine (allowed_cidr)
      │ HTTPS 443 (self-signed certificate, hostname)    │ PostgreSQL 5432 (setup.sh, verify-env.sh)
      ▼                                                  ▼
  ALB (internet-facing, public subnets) ──►  dbgateway tasks ×2  ──►  RDS for PostgreSQL 17 (public subnets)
                               HTTP 8443     (Fargate ARM64,          - app       target database (IAM auth)
                                              private subnets)        - dbgateway management database + audit log
                                                    │
                                                    └─ ECR, Secrets Manager, CloudWatch Logs via the NAT gateway
```

- VPC `10.42.0.0/16` (public / private subnets in two AZs, an internet gateway, one NAT gateway)
- RDS for PostgreSQL 17 (`db.t4g.micro`, encrypted, `rds.force_ssl=1`, IAM database authentication enabled). Public access is enabled so that `setup.sh` can run from `allowed_cidr`, but the security group admits only `allowed_cidr` and the dbgateway tasks. No backups, no final snapshot, no deletion protection
  - Database `app`: the target database, with the sample schema (`examples/dev/initdb/01-schema.sql`) and the IAM-authenticated users `dbgw_iam` (read) and `dbgw_iam_writer` (write)
  - Database `dbgateway`: the management database and audit log (owner `dbgw_store`, password generated by Terraform). In production, put the management database on a separate instance from the target databases ([high availability](../../docs/ha.md)); here they share one instance to keep costs down
- An ECR repository (deleted together with its images), an ECS cluster, a Fargate service (ARM64, 0.5 vCPU / 1 GB, 2 tasks), and a CloudWatch Logs log group (1-day retention)
- An ALB (accepts HTTPS 443 only from `allowed_cidr`, using a self-signed certificate for `hostname` imported into ACM). The target group uses IP targets, port 8443, and the health check `GET /healthz`
- IAM
  - Task role: only `rds-db:connect` for `dbgw_iam` and `dbgw_iam_writer`
  - Task execution role: only pulling images from this ECR repository, writing to this log group, and reading the secret that holds the management database DSN
- Secrets Manager: the management database DSN (the task's `DBGW_STORE_DSN` environment variable). Deleted without a recovery window on destroy

The dbgateway configuration is rendered from `templates/dbgateway.yaml.tftpl` and passed in the `DBGW_CONFIG_YAML` environment variable (it contains no secrets; view it with `terraform output -raw dbgateway_config`). Users sign in with passkeys (no IdP), writes require approval, and the management database and audit log are on PostgreSQL. `requester_email` is a member of `developers` (querier, writer) and `approver_email` a member of `approvers` (querier, writer, approver).

### RDS CA certificates

The tasks receive the RDS CA certificates for the region (`https://truststore.pki.rds.amazonaws.com/<region>/<region>-bundle.pem`, three certificates) in the `DBGW_DB_CA` environment variable, used through `sslrootcert_env` in the configuration. The bundle for all regions (about 170 KB) does not fit within the ECS task definition limit (64 KiB including environment variables). The instance certificate is issued by `rds-ca-rsa2048-g1`, which is included in the regional bundle. Locally (`setup.sh`, `verify-env.sh`), the all-regions bundle `rds-global-bundle.pem` is used.

## Cost

Roughly 0.2 USD per hour (about 5 USD per day) in the Tokyo region. The main items are the NAT gateway, the ALB, RDS, two Fargate tasks and public IPv4 addresses (an estimate; check current pricing). Destroy the environment as soon as you are done.

## Variables

| Variable | Default | Description |
| --- | --- | --- |
| `allowed_cidr` | (required) | CIDR allowed to reach the ALB and RDS: the public IP of your test machine (`x.x.x.x/32`). `0.0.0.0/0` is rejected |
| `requester_email` | (required) | Requester's email address (group `developers`) |
| `approver_email` | (required) | Approver's email address (group `approvers`; must differ from `requester_email`) |
| `image` | `""` | dbgateway image (linux/arm64, in this ECR repository). When empty, the service runs zero tasks (so that ECR can be created and the image pushed first) |
| `desired_count` | `2` | Number of tasks when `image` is set. Two tasks verify sharing of the management database |
| `hostname` | `dbgw.test` | dbgateway host name (`server.public_url` and the certificate). Not registered in DNS; point it at the ALB on your test machine |
| `region` | `ap-northeast-1` | Region |
| `name` | `dbgw-ecs-test` | Prefix for resource names |
| `vpc_cidr` | `10.42.0.0/16` | VPC CIDR |
| `engine_version` / `instance_class` | `17` / `db.t4g.micro` | RDS |

Main outputs: `alb_dns_name`, `ecr_repository_url`, `rds_host`, `hostname`, `public_url`, `tls_cert_pem` (the self-signed certificate; trust it on the client), `dbgateway_config`, `cluster_name`, `service_name`, `log_group`, `region`, `requester_email`, `approver_email`, and the sensitive `admin_password`, `store_password` and `store_dsn` (a management database DSN that also works from your machine with the same host).

## Steps

Requirements: Terraform 1.9 or later, the AWS CLI with credentials, Docker, Go, curl. Unless noted otherwise, run commands in `deploy/aws-ecs`.

**1. Prepare variables**

```sh
cd deploy/aws-ecs
export AWS_PROFILE=<your-profile>          # or any other credential source
cat > terraform.tfvars <<EOF
allowed_cidr    = "$(curl -fsSL https://checkip.amazonaws.com)/32"
requester_email = "<requester@example.com>"
approver_email  = "<approver@example.com>"
EOF
```

**2. Initialize and review the plan**

```sh
terraform init
terraform plan -out tfplan                 # review the resources to be created
```

**3. Create (no image, zero tasks)**

```sh
terraform apply tfplan
```

Creating RDS takes about 10 minutes.

**4. Prepare the databases**

```sh
./setup.sh
```

Using `docker run postgres:17 psql` (`sslmode=verify-full`), this creates the sample schema in `app` (if missing) and the IAM users `dbgw_iam` and `dbgw_iam_writer`, plus the `dbgw_store` role and the `dbgateway` database. It is idempotent. The password user `dbgw_reader` created by the sample schema is not used in this environment, so it is prevented from logging in.

Run it before starting the tasks: a task fails to start if it cannot connect to the management database (if you run it afterwards, the tasks start working as ECS restarts them).

**5. Build and push the image**

At the repository root, build a linux/arm64 image and push it to ECR with `deploy.sh`. `deploy.sh` neither builds nor runs `terraform apply`.

```sh
cd ../..
docker buildx build --platform linux/arm64 -t dbgateway:$(git rev-parse --short HEAD)-arm64 --load .
deploy/aws-ecs/deploy.sh dbgateway:$(git rev-parse --short HEAD)-arm64
```

**6. Start the tasks**

Run the commands printed by `deploy.sh` (the image is referenced by digest).

```sh
cd deploy/aws-ecs
terraform plan -var 'image=<ecr_repository_url>@sha256:...' -out tfplan   # review the task definition and service changes
terraform apply tfplan
aws ecs wait services-stable --cluster "$(terraform output -raw cluster_name)" --services "$(terraform output -raw service_name)"
```

Pass the same `-var image=...` on every later `terraform apply` (without it, the service scales to zero tasks). View logs with `aws logs tail "$(terraform output -raw log_group)" --follow`.

**7. Generate the test environment variables**

Run at the repository root.

```sh
cd ../..
set -a; eval "$(deploy/aws-ecs/verify-env.sh)"; set +a
```

`verify-env.sh` prints the following variables.

| Variable | Value |
| --- | --- |
| `DBGW_CLOUD_URL` | `https://<hostname>` |
| `DBGW_CLOUD_CONNECT_ADDR` | `<alb_dns_name>:443` (where to connect instead of `hostname`) |
| `DBGW_CLOUD_CA_FILE` | Absolute path of the file holding the ALB's self-signed certificate (`deploy/aws-ecs/alb-cert.pem`) |
| `DBGW_CLOUD_DB` | `cloud-main` |
| `DBGW_CLOUD_ENROLL_REQUESTER` / `DBGW_CLOUD_ENROLL_APPROVER` | Passkey enrollment links for the requester and approver (one-time, valid for 24 hours) |

The enrollment links are created by connecting to the management database from your machine with the command below (`dbgw passkey enroll` loads the configuration, so it needs `DBGW_DB_CA` for `sslrootcert_env`; the IAM-authenticated target database needs no secret).

```sh
DBGW_CONFIG_YAML="$(terraform -chdir=deploy/aws-ecs output -raw dbgateway_config)" \
DBGW_STORE_DSN="$(terraform -chdir=deploy/aws-ecs output -raw store_dsn)" \
DBGW_DB_CA="$(cat deploy/aws-ecs/rds-global-bundle.pem)" \
  go run ./cmd/dbgw passkey enroll --config env:DBGW_CONFIG_YAML --email <email>
```

To try it in a browser, map `hostname` in `/etc/hosts` to one of the IP addresses from `dig +short "$(terraform output -raw alb_dns_name)"`, and trust `alb-cert.pem` (the ALB's IP addresses can change).

**8. Run the tests**

```sh
go test -tags cloud -count=1 ./test/cloud/
```

**9. Destroy**

```sh
cd deploy/aws-ecs
terraform plan -destroy -out tfplan        # review the resources to be destroyed
terraform apply tfplan
```

This also deletes the ECR images, the Secrets Manager secret (no recovery window) and RDS (no snapshot). Delete the local `terraform.tfvars`, `rds-global-bundle.pem` and `alb-cert.pem` as needed.

## Security notes

- For testing only. The ALB (443) and RDS (5432) are reachable only from `allowed_cidr`. Set `allowed_cidr` to the `/32` of your own public IP. If your IP address changes, update `terraform.tfvars` and apply again
- The ALB certificate is a self-signed certificate created by Terraform (valid for 30 days). Its private key is stored in the Terraform state. The state also contains the RDS master password and the management database password and DSN, so do not share it
- RDS has public access enabled (for running `setup.sh` from `allowed_cidr`). In production, place it in private subnets and disable public access
- The dbgateway tasks accept only HTTP from the ALB (inside the VPC). Their only outbound traffic is HTTPS (through NAT) and PostgreSQL to RDS
- A passkey enrollment link is a secret: whoever holds it can register a passkey as that person. Do not leave it in logs or shared places
